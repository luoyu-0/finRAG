# 系统接口

本文档集中维护当前已实现接口和计划中的核心契约。除健康检查、登录和刷新会话外，业务接口默认要求鉴权；新增业务接口时必须标明允许角色和资源归属规则。

## 1 通用约定

- API 统一位于 `/api/v1`。
- JSON 字段使用 `snake_case`，时间使用带时区的 ISO 8601 字符串并按 UTC 保存。
- Access Token 通过 `Authorization: Bearer <token>` 发送。
- Refresh Token 通过 `HttpOnly` Cookie 传递，不进入 JSON 响应或浏览器存储。
- `401 Unauthorized` 表示未登录、凭据无效或会话过期；`403 Forbidden` 表示身份有效但权限不足。
- 错误至少包含稳定的 `error_code` 和可读 `message`，不得返回密码、Token、Cookie 或异常堆栈。

错误示例：

```json
{
  "error_code": "AUTH_INVALID_CREDENTIALS",
  "message": "用户名或密码错误"
}
```

## 2 后端健康检查

- 方法：`GET`
- 路径：`/api/v1/health`
- 鉴权：无
- 状态：已实现

成功响应：

```json
{
  "status": "ok",
  "service": "backend"
}
```

该接口只表示 FastAPI 进程可以响应，不代表 MySQL、Milvus、DeepSeek 或 OCR 已通过业务级检查。深度健康检查应使用独立接口，避免改变本接口的轻量语义。

## 3 鉴权接口草案

以下接口尚未实现，供前后端并行开发；字段在数据库模型落地前仍可通过评审调整。

### 3.1 登录

- 方法：`POST`
- 路径：`/api/v1/auth/login`
- 鉴权：无

请求：

```json
{
  "username": "demo_user",
  "password": "用户输入的密码"
}
```

成功响应：

```json
{
  "access_token": "短时访问令牌",
  "token_type": "bearer",
  "expires_in": 900,
  "user": {
    "id": "用户 ID",
    "username": "demo_user",
    "display_name": "演示用户",
    "role": "user",
    "status": "active"
  }
}
```

响应同时设置 Refresh Cookie。用户名不存在、密码错误、账户禁用或锁定时返回统一登录失败信息。

### 3.2 刷新会话

- 方法：`POST`
- 路径：`/api/v1/auth/refresh`
- 鉴权：Refresh Cookie

成功时轮换 Refresh Token 并返回新的 Access Token。Refresh Token 缺失、过期、已撤销或重复使用时返回 `401`，必要时撤销同一 Token 家族。

### 3.3 退出登录

- 方法：`POST`
- 路径：`/api/v1/auth/logout`
- 鉴权：Access Token 或 Refresh Cookie

撤销当前 Refresh Session 并清除 Cookie。接口保持幂等，重复退出不返回内部错误。

### 3.4 修改密码

- 方法：`POST`
- 路径：`/api/v1/auth/change-password`
- 鉴权：`user`、`admin`

请求：

```json
{
  "current_password": "当前密码",
  "new_password": "新密码"
}
```

修改成功后撤销该用户的其他 Refresh Session。

## 4 用户接口草案

### 4.1 获取当前用户

- 方法：`GET`
- 路径：`/api/v1/users/me`
- 鉴权：`user`、`admin`

返回当前用户的 ID、用户名、展示名称、角色和状态，不返回密码哈希或会话 Token。

### 4.2 修改当前用户

- 方法：`PATCH`
- 路径：`/api/v1/users/me`
- 鉴权：`user`、`admin`

第一阶段只允许修改 `display_name`，用户名和角色由管理员接口维护。

### 4.3 创建用户

- 方法：`POST`
- 路径：`/api/v1/users`
- 鉴权：`admin`

请求包含 `username`、初始密码、`display_name` 和 `role`。日志和响应不得回显初始密码。

### 4.4 用户列表

- 方法：`GET`
- 路径：`/api/v1/users`
- 鉴权：`admin`

支持分页，并可按用户名、角色和状态筛选。

### 4.5 更新用户

- 方法：`PATCH`
- 路径：`/api/v1/users/{user_id}`
- 鉴权：`admin`

允许修改展示名称、角色和状态。禁用用户后立即撤销其 Refresh Session；不得通过普通流程禁用系统中最后一个可用管理员。

### 4.6 撤销用户会话

- 方法：`DELETE`
- 路径：`/api/v1/users/{user_id}/sessions`
- 鉴权：`admin`

撤销指定用户全部 Refresh Session，用于账户异常、密码重置或权限变更后的强制退出。

## 5 鉴权错误码

| 错误码 | HTTP 状态 | 含义 |
| --- | ---: | --- |
| `AUTH_INVALID_CREDENTIALS` | 401 | 登录凭据无效 |
| `AUTH_TOKEN_EXPIRED` | 401 | Access Token 已过期 |
| `AUTH_SESSION_INVALID` | 401 | Refresh Session 无效或已撤销 |
| `AUTH_ACCOUNT_UNAVAILABLE` | 401 | 账户不可用 |
| `AUTH_FORBIDDEN` | 403 | 当前用户无权执行操作 |
| `USER_USERNAME_CONFLICT` | 409 | 用户名已存在 |
| `USER_LAST_ADMIN_REQUIRED` | 409 | 操作会导致系统无可用管理员 |

## 6 RAG 问答接口草案

- 方法：`POST`
- 路径：`/api/v1/qa/answer`
- 鉴权：`user`、`admin`
- 状态：核心编排已实现；鉴权、检索器和生成 Provider 接入后再挂载 HTTP 路由

请求：

```json
{
  "question": "商业银行应如何管理流动性风险？",
  "knowledge_base_ids": ["金融监管制度库"],
  "effective_at": "2026-10-10T00:00:00+08:00",
  "top_k": 8
}
```

`effective_at` 为空时使用请求发生时间。默认只检索在目标时间有效的制度版本；是否允许查询历史失效制度应通过后续独立参数和权限评审，不由提示词临时决定。

成功响应：

```json
{
  "answer": "基于当前检索证据生成的回答。",
  "citations": [
    {
      "label": "S1",
      "document_id": "doc_001",
      "version_id": "ver_001",
      "chunk_id": "chunk_001",
      "title": "制度标题",
      "page_number": 12,
      "article_number": "第二十条",
      "source_url": "https://example.org/policy.pdf"
    }
  ],
  "evidence_support": {
    "score": 0.82,
    "level": "strong",
    "method": "retrieval_evidence_v1",
    "explanation": "表示当前检索证据对回答的支持程度，不是答案正确概率。"
  },
  "warnings": [],
  "trace_id": "请求追踪 ID"
}
```

未检索到有效证据时返回 `200`，提供明确的无依据回答、空引用和 `none` 支持等级，不调用 LLM 猜测答案。所有检索通道不可用时返回 `503 RAG_RETRIEVAL_UNAVAILABLE`；生成 Provider 不可用或返回越界引用时返回 `502 RAG_GENERATION_FAILED`。
