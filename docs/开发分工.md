# 金融制度 RAG 项目开发分工

## 1 分工原则

项目共四人协作，其中三人承担主要开发工作，一人主要承担文档、过程材料与答辩工作。角色先使用 A、B、C、D 代称，确定姓名和学号后再替换。

每个模块设置一名主要负责人，但不形成知识孤岛。主要负责人负责方案、实现质量、测试和交付说明；涉及其他模块时，由接口提供方先定义契约，使用方参与评审。任何成员修改他人负责模块前，应先同步变更目的和影响范围。

## 2 总体责任矩阵

| 角色 | 主要职责 | 主责目录 | 关键交付物 |
| --- | --- | --- | --- |
| 开发 A | 架构、后端 API、RAG 与存储集成 | `backend/app/api`、`core`、`domain`、`repositories`、`schemas`、`services/rag`、`infra/mysql`、`infra/milvus` | 系统架构、API、混合检索、问答编排、MySQL 与 Milvus 接入 |
| 开发 B | 文档处理、OCR、知识库和评测数据 | `backend/app/services/documents`、`services/ocr`、`workers`、`data`、相关后端测试 | 文档解析、PaddleOCR/Tesseract 适配、分段、Embedding、索引导入与知识库维护 |
| 开发 C | 前端、联调、测试与部署集成 | `frontend`、`frontend/tests`、`backend/tests/integration`、`infra/docker`、`infra/nginx` | Web 界面、接口客户端、端到端测试、性能测试、Compose 集成和部署验证 |
| 文档 D | 需求、过程文档、用户手册与答辩 | `docs`，不含由接口负责人维护的技术契约正文 | 开题、中期、验收、用户手册、测试与指标汇总、答辩 PPT 和演示脚本 |

架构决策、接口契约、数据安全和最终验收由全员共同评审，不归单一角色独占。

## 3 开发 A 详细职责

### 3.1 系统架构

- 绘制系统上下文、容器和核心组件关系图。
- 明确 FastAPI、MySQL、Milvus、LLM、Embedding、OCR 和异步任务之间的边界。
- 定义配置加载、日志、异常响应、认证预留和依赖注入方式。
- 控制 LangChain 的使用边界，避免领域模型直接依赖复杂编排对象。

### 3.2 后端接口

- 设计 API 版本和统一响应、错误码及分页格式。
- 提供文档上传、导入任务状态、知识库管理、问答、来源详情、历史记录和收藏接口。
- 与开发 C 共同确认接口字段，与开发 B 共同确认导入任务和知识条目模型。
- 维护 `docs/api/` 下的接口契约；文档 D 负责将其整理进课程交付材料，但不替代接口负责人维护技术事实。

### 3.3 RAG 与存储

- 实现关键词检索、向量检索、过滤、融合、重排和上下文组装流程。
- 设计条文溯源、有效期过滤和可信度评分的统一输出结构。
- 负责 MySQL 业务表、Milvus Collection 及两类数据 ID 映射规则。
- 抽象 LLM 和 Embedding Provider，确保模型可替换并支持测试替身。

### 3.4 质量责任

- 为核心服务和数据访问层编写单元测试。
- 对查询路径进行耗时分解，推动达到在线问答两秒目标。
- 审查开发 B 提交的索引数据结构，以及开发 C 提交的 API 调用变更。

## 4 开发 B 详细职责

### 4.1 文档接入

- 识别文本、PDF、图片等输入类型，并保留来源文件、页码和条文编号等元数据。
- 文本型 PDF 优先直接提取文字；无有效文本层的页面进入 OCR 流程。
- 设计清洗、段落合并、标题识别、条文切分和重复内容处理规则。
- 建立文件哈希、解析版本和索引版本，为增量更新与幂等导入提供基础。

### 4.2 OCR

- 定义统一 `OCRProvider` 契约。
- 以 PaddleOCR 处理中文扫描件和复杂版面，以 Tesseract 作为轻量备用方案与效果基线。
- 保存文本框、置信度、页码和必要的版面信息，避免只保留纯文本。
- 对低置信度页面提供人工复核标记，不将 OCR 置信度直接等同于最终答案可信度。

### 4.3 知识库构建

- 负责分段、Embedding 批处理、标签生成和 Milvus 写入准备。
- 与开发 A 共同确定 Chunk、Document、PolicyVersion、Citation 等对象的字段。
- 实现制度生效、失效和被替代关系的数据准备规则。
- 维护可重复执行的数据导入流程及失败重试策略。

### 4.4 评测数据

- 从获准使用的公开金融制度材料中整理代表性样本。
- 与文档 D 共同建立问题、标准答案、对应条文和有效期信息。
- 分别记录 OCR 字符错误、检索命中、引用正确性和最终回答准确性，避免只用单一指标评价系统。

## 5 开发 C 详细职责

### 5.1 前端功能

- 建立 React 与 TypeScript 工程规范、路由、状态管理和 API 客户端边界。
- 实现知识库管理、文档上传与任务进度、问答、来源查看、历史记录和收藏页面。
- 明确展示答案来源、条文状态和可信度，避免将模型输出呈现为无条件正确的结论。
- 处理加载、空数据、失败、超时和任务重试等状态。

### 5.2 联调与测试

- 根据 `docs/api/` 契约生成或维护前端类型，不以临时字段绕过契约。
- 负责主要用户流程的端到端测试，并协助补充后端接口集成测试。
- 汇总响应时间、并发行为和失败率，区分在线问答耗时与离线文档导入耗时。
- 建立可重复的缺陷记录与回归检查清单。

### 5.3 部署

- 维护前端、后端容器构建配置和 Docker Compose 集成。
- 组织 MySQL、Milvus、API、前端及必要依赖的健康检查和启动顺序。
- 提供环境变量示例和最少启动步骤，确保新成员不必在宿主机单独安装数据库与 OCR 工具。
- 与开发 A、B 分别确认服务配置和模型文件的持久化需求。

## 6 文档 D 详细职责

### 6.1 过程文档

- 维护需求范围、术语表、会议纪要、进度、风险和决策记录。
- 根据实际代码和测试结果撰写开题报告、中期报告、验收报告与总结报告。
- 主动向各模块负责人收集可验证材料，不推测技术实现、测试指标或完成状态。
- 保证文档、演示界面、接口名称和实际系统保持一致。

### 6.2 用户材料

- 编写面向普通使用者的安装、启动、文档导入、问答、溯源和常见问题说明。
- 与开发 C 验证每项操作步骤，与开发 A、B 核对技术说明。
- 整理数据来源、授权边界、隐私与安全说明。

### 6.3 答辩准备

- 设计答辩 PPT 的问题背景、目标指标、架构、创新点、演示、评测和总结结构。
- 编排演示脚本、备用截图或录屏以及故障预案。
- 汇总常见技术问题并组织预演，各模块技术问题由对应开发成员负责回答。

## 7 模块交接约定

### 7.1 开发 B 向开发 A

知识库导入结果至少应提供：文档 ID、版本 ID、Chunk ID、正文、标题层级、页码、条文编号、生效状态、来源链接、标签、Embedding 状态和解析告警。字段在写入实现前共同评审。

### 7.2 开发 A 向开发 C

每个接口至少应明确：方法与路径、请求字段、响应字段、错误码、分页方式、任务状态、超时行为和示例。接口发生不兼容变更时，应先更新契约并通知开发 C。

### 7.3 全体向文档 D

每个阶段结束时，各负责人提交功能清单、架构变化、测试结果、遗留问题和可演示步骤。文档 D 负责组织和表达，不负责替开发人员虚构缺失数据。

## 8 阶段计划

| 阶段 | 时间 | 开发重点 | 文档与答辩重点 | 阶段出口条件 |
| --- | --- | --- | --- | --- |
| 选题与设计 | 第 1-4 周 | 需求边界、架构、数据模型、API 草案、评测口径 | 开题报告、技术路线图、开题答辩 | 核心方案评审通过，样例数据来源合法可用 |
| 核心开发 | 第 5-8 周 | 文档解析、OCR、分段、Embedding、MySQL 与 Milvus 原型 | 记录方案、数据来源和阶段问题 | 至少一批文档可重复导入并完成检索 |
| 中期集成 | 第 9-10 周 | RAG 问答、来源引用、后端 API、初步联调与测试 | 中期报告、中期演示 | 完成知识库和核心检索，中期演示可运行 |
| 完整功能 | 第 11-12 周 | 前端、历史、收藏、有效期管理、增量更新 | 用户手册初稿、功能截图 | 主要用户流程端到端可用 |
| 优化验收 | 第 13-15 周 | 准确率、响应时间、稳定性、测试覆盖率和缺陷修复 | 验收报告、总结报告、答辩 PPT | 指标有可复现测试结果，严重缺陷关闭 |
| 最终提交 | 第 16 周 | 发布包、环境复核和演示保障 | 正式答辩、材料归档 | 新环境可按文档部署并完成演示 |

## 9 Git 协作流程

1. 从主分支同步最新代码后创建短生命周期分支。
2. 分支名称采用 `feature/<模块>-<说明>`、`fix/<模块>-<说明>` 或 `docs/<说明>`。
3. 提交前运行所属模块的格式检查和测试，不提交密钥、模型大文件、数据库数据或本地缓存。
4. Pull Request 写明变更目的、影响范围、验证方法、接口变化和待办事项。
5. 至少由一名非作者成员审查；跨模块变更必须包含受影响模块的负责人。
6. 合并后由提交者关注持续集成结果，并处理由本次变更造成的回归。

## 10 完成标准

一项开发任务只有同时满足以下条件才视为完成：

- 功能行为与已确认需求或接口契约一致。
- 核心路径有自动化测试，测试可在统一环境重复执行。
- 错误、空数据和超时场景得到处理。
- 不包含密钥、敏感数据、无授权材料或不必要的大文件。
- 必要的接口、架构、使用方式和限制已经更新到对应文档。
- 由至少一名非作者成员完成审查，且没有未处理的阻断问题。

## 11 首轮待确认事项

- 四名成员的姓名、学号和角色对应关系。
- 首批制度数据来源、许可范围和用于人工评测的样本规模。
- LLM 与 Embedding 的首选实现、费用限制和离线备用方案。
- 问答准确率、响应时间和可信度评分的正式计算口径。
- 演示及最终部署环境的 CPU、内存、GPU 和网络条件。
