### 2.1 第 8 项的数据探针方法（可复现）

仅确认容器能重启不足以证明数据落盘，因此使用真实数据标记：

```powershell
# ① 在 Milvus 中创建探针 collection
POST http://127.0.0.1:19530/v2/vectordb/collections/create
{ "collectionName": "finrag_persistence_probe", "dimension": 8, "metricType": "COSINE" }

# ② 确认存在
POST http://127.0.0.1:19530/v2/vectordb/collections/list   →  data: finrag_persistence_probe

# ③ 销毁容器与网络（绝对不加 -v，-v 会删除数据卷）
docker compose down
docker compose up -d

# ④ 复查：探针仍在即证明重新挂载的是原有命名卷
POST http://127.0.0.1:19530/v2/vectordb/collections/list   →  data: finrag_persistence_probe
```

结果：`docker compose down` 输出仅移除 6 个容器与 1 个网络，**四个命名卷未被移除**；重建后探针 collection 依然存在，判定持久化生效。验收后探针已删除，Milvus 恢复为空。

## 3 本次改动专项验证（Nginx 加固）

这三项是本轮新增配置，单独做了针对性验证。

| 改动 | 验证方法 | 结果 |
| --- | --- | --- |
| `client_max_body_size 50m` | 向 `:3000/api/v1/health` POST 2 MB 与 60 MB 请求体 | ✅ 2 MB → **HTTP 405**（已转发到后端，未被拒绝）；60 MB → **HTTP 413**（超出上限被拒）。对照直连 `:8000` 的 2 MB → 405，证明 413 完全由 Nginx 控制 |
| `gzip on` | 请求 `/assets/*.js` 并带 `Accept-Encoding: gzip` | ✅ 响应头 `Content-Encoding: gzip` |
| 静态资源长缓存 | 同上，检查响应头 | ✅ `Cache-Control: max-age=31536000,public, immutable` |

> 2 MB 得到 405 是 FastAPI 对 `POST /api/v1/health`（仅允许 GET）的正常响应，说明请求体已被完整转发 —— 若上限仍是默认的 1m，此处会直接返回 413。

## 6 结论

在 Windows 11 + Docker Desktop 环境下，`docker compose up -d --build` 可一次性完成全部镜像构建与六个服务启动，所有服务进入 `healthy`，四个对外端点与两项探针全部通过，数据卷持久化经真实数据探针验证生效。本轮新增的 Nginx 加固配置经针对性测试确认生效。
