# 后端单元测试与覆盖率

本文记录后端测试的运行方式、当前结果与覆盖率口径，供阶段材料与验收引用。

## 1 目的与范围

- 运行方式可复现：任何成员按本文命令即可得到一致结果。
- 覆盖率口径明确：说明"核心模块"的范围、当前达成情况，以及为何暂时不设硬门槛。
- 结果与 CI 一致：本文记录的命令与 `.github/workflows/ci.yml` 的 backend 作业完全相同。

当前范围仅覆盖已实现的后端 RAG 在线核心（领域模型、融合、评分、上下文组装、编排与问答 Schema）。鉴权、文档解析、检索器与生成 Provider 尚未实现，不在本次统计范围内。

## 2 运行方式

后端测试依赖独立于生产依赖，配置在 `backend/requirements-dev.txt` 与 `backend/pyproject.toml`。

```bash
cd backend

# 1 创建独立虚拟环境（Python 3.12，与后端镜像 python:3.12-slim 一致）
python -m venv .venv

# 2 激活虚拟环境
#    Windows PowerShell:  .venv\Scripts\Activate.ps1
#    Linux / macOS:       source .venv/bin/activate
#
#    若 Windows 执行策略禁止运行脚本（与 npm.ps1 同类问题），可跳过激活，
#    把下文命令中的 python 换成虚拟环境解释器：
#    Windows 用 .venv\Scripts\python.exe，Linux / macOS 用 .venv/bin/python。

# 3 安装依赖
python -m pip install --requirement requirements-dev.txt

# 4 运行单元测试
python -m pytest -v

# 5 运行单元测试并生成覆盖率报告
python -m pytest --cov=app --cov-report=term-missing --cov-report=xml
```

生产镜像只安装 `requirements.txt`，测试工具不会进入镜像。CI 使用同一组命令。

### 3.2 用例覆盖的行为

- 融合去重与通道记录（RRF）
- 生成前过滤失效与不匹配的制度版本
- 无有效证据时不调用 LLM，返回明确的"无依据"回答
- 单条检索通道故障时降级并记录告警
- 全部检索通道故障时返回检索不可用错误
- 生成器引用未知标签、未返回引用、返回空回答时拒绝
- 可选重排器失败时退回融合排名
- `effective_at` 强制要求时区、问题文本归一化

## 4 覆盖率口径

### 4.1 目标与当前状态

课程要求核心模块单元测试覆盖率不低于 **70%**（NFR-4）。当前已达 **83%**，**超过目标**，但这一数字只覆盖已实现的后端 RAG 核心。

### 4.2 为什么暂不设 `fail_under` 硬门槛

- 覆盖率统计口径中的 `app/main.py`（0%）等模块尚无测试，业务接口与鉴权也未实现；
- 若立即硬卡 70%，流水线会在后续模块尚未落地时长期变红，失去信号价值；
- 因此当前策略与前端一致：**先只统计与展示，不设 fail 门槛**，待业务模块与测试就位后逐步抬升并在 CI 中硬卡。

### 4.3 "核心模块"的界定

在最终评测口径确定前，暂按以下范围界定并随实现扩展：

- `app/domain/`：领域模型与规则
- `app/services/`：业务服务（RAG、鉴权、文档处理）
- `app/repositories/`：数据访问抽象
- `app/schemas/`：接口请求与响应模型

`app/main.py` 等纯装配代码不计入核心模块。

## 5 CI 集成

`.github/workflows/ci.yml` 的 `backend` 作业在每次 push 到 `main` 与每次 PR 时执行：

```bash
pip install --requirement requirements-dev.txt
pytest --cov=app --cov-report=term-missing --cov-report=xml
```

覆盖率报告以 `coverage.xml` 形式上传为构建产物（`backend-coverage`）。`coverage.xml` 与 `.coverage` 均已加入 `.gitignore`，不进入版本库。
