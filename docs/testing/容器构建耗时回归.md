# 容器构建耗时回归

验证日期：2026-10-27。环境：Windows 11、Docker Desktop、本地 Compose。

## 问题与原因

用户执行 `docker compose up -d --build --wait` 时，后端镜像的 Debian 软件源步骤在下载约 9.7 MB 的包索引上停留超过 129 秒。原配置将主仓库指向 `ftp.debian.org`；最小构建探针复现了连接失败：`apt-get update` 用时 24.6 秒，主仓库索引未获取成功，却仍以退出码 0 结束。

这一步安装 `libgl1`、`libglib2.0-0` 和 `libgomp1`。`python:3.12-slim` 不提供对应运行库；此前 OCR 实际运行曾分别因缺少 `libGL.so.1` 和 `libgomp.so.1` 失败，因此不能直接删除系统库安装。

## 调整与结果

- Compose 构建参数默认选用清华 Debian 镜像站，同时允许通过 `.env` 覆盖主仓库与安全仓库地址；直接使用 Dockerfile 时默认仍为 Debian 官方 CDN。
- `apt-get update` 启用 `APT::Update::Error-Mode=any`，任一软件源索引获取失败即中止构建，不再静默继续。
- Windows 启动脚本默认复用已有镜像；首次构建或源码、依赖变化时显式使用 `./scripts/start.ps1 -Build`。

| 验证 | 结果 |
| --- | --- |
| 最小探针，原 `ftp.debian.org` 主仓库 | 24.6 秒；主索引获取失败，旧命令仍返回 0 |
| 最小探针，清华主仓库与安全仓库 | 索引下载 3 秒，整个更新 3.6 秒，成功 |
| 完整首次重建并启动 | Debian 索引与系统库安装 17.6 秒；总耗时约 281 秒，主要剩余耗时为 BGE 模型下载与镜像导出；六项服务均健康 |
| 同配置再次强制重建并启动 | 8.6 秒；Debian、Python 依赖、BGE 均命中构建缓存 |
| 日常启动，不强制重建 | 3.6 秒；六项服务均健康 |

最终后端镜像内 `paddle` 3.3.1 与 OpenCV 4.10.0 均可导入。上述时长受本地网络、Docker 缓存和机器负载影响；首次下载 BGE 模型仍可能较慢，后续同配置构建可复用缓存。

## 2026-10-28 GitHub Actions 构建失败

`main` 的容器集成作业在后端镜像执行 `apt-get update` 时无法连接 Compose 默认的清华镜像站，构建以退出码 100 结束。CI 作业现通过构建参数使用 Debian 官方软件源；本地 Compose 默认镜像站保持不变。

验证：以 CI 的软件源参数解析 Compose 配置，后端构建参数均指向 `deb.debian.org`；在本地 Docker 中，官方源的 `apt-get update` 和三个系统库安装成功，`docker compose build backend` 成功。GitHub Actions 仍需在提交后重跑确认。
