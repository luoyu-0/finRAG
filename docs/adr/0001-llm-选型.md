# ADR-0001 LLM 选型

- **状态**：提议（见「待确认」）
- **日期**：2026-10-12
- **决策者**：项目组
- **相关**：[系统架构](../architecture/系统架构.md) · [开发分工](../开发分工.md) · [系统接口](../api/系统接口.md) · [术语表](../../GLOSSARY.md)

## 背景

项目需要确定生成回答所用的 LLM，同时保留后续替换模型供应商与档位的能力。

课程命题《创新实践课程校企合作企业命题-信雅达》在「核心技术栈」的"其他关键技术"一栏中写明：

> Tesseract（OCR）、开源 LLM（通义千问 / ChatGLM）—— OCR 解析图片类文档，**LLM 选择开源可商用版本**。

## 决策

1. **LLM 初始使用 DeepSeek 远程 API。** API Key 只从环境变量 `DEEPSEEK_API_KEY` 读取，不写入镜像或仓库。
2. **通过 Provider 接口隔离**：`AnswerGenerator` 为生成端口，业务代码不直接调用厂商 SDK。

## 考虑的替代方案

| 方案 | 结论 |
| --- | --- |
| 本地部署开源模型（通义千问 / ChatGLM） | 符合命题字面要求，但需要 GPU 与显存资源，且本地推理耗时对「问答响应 ≤2 秒」的目标构成压力。在当前硬件（Windows 11 家庭版个人电脑）上不具备可行性，暂不采用。 |
| 业务代码直接调用厂商 SDK | 否决。与协作规范「LLM、Embedding、OCR 和向量库通过 Provider 或 Repository 接口隔离，不在业务代码中散落厂商调用」冲突。 |

## 后果

**正面**

- 无需本地 GPU 即可起步，链路验证不被硬件阻塞。
- 接口隔离使 LLM 替换只需新增一个 Provider 实现，不影响业务代码与测试。
- 单元测试可使用 Stub 生成器，不真实调用收费 API（符合测试规范）。

**负面**

- 数据出境与合规方面的表述需要在文档中明确说明。
- 依赖外部服务的可用性与配额；服务不可用时问答链路降级（契约中已定义 `502 RAG_GENERATION_FAILED`）。
- 成本随调用量增长。

**待确认**

> **命题要求「开源可商用 LLM」，与本决策采用的 DeepSeek 闭源远程 API 不一致。该冲突目前尚未获得企业导师确认。**
>
> 若最终必须改用开源模型，需要重新评估的不只是 Provider 实现，还包括：本地推理的硬件与部署形态、容器编排是否需要新增推理服务、以及「响应 ≤2 秒」目标的可达性。因此该事项应当在生成 Provider 实现**之前**澄清，避免返工。
