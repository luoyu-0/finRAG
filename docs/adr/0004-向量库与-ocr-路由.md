# ADR-0004 向量库与选择性 OCR 路由

- **状态**：已接受
- **日期**：2026-10-12
- **决策者**：项目组
- **相关**：[系统架构](../architecture/系统架构.md) · [容器架构说明](../architecture/系统架构.md) · [术语表](../../GLOSSARY.md)

## 背景

两个相互独立但都与文档处理相关的问题需要在早期定下来：

1. **向量存储选型。** 混合检索需要保存制度分块的向量并在查询时检索。
2. **扫描件处理策略。** 命题要求支持「文本、PDF、图片（OCR 解析）」，但金融制度材料以 PDF 为主，其中既有带文本层的文本型 PDF，也有纯扫描件。全量 OCR 代价高，且会引入本可避免的识别错误。

## 决策

**向量存储**

- 使用 **Milvus Standalone**，配合 `etcd`（元数据）与 `MinIO`（对象数据），随 Docker Compose 一并启动。
- MySQL 保存业务状态与元数据，Milvus 保存向量及检索所需字段，两者通过稳定 ID 关联。

**文档处理**

- 采取**选择性 OCR 路由**：`原生文本提取优先 → 逐页质量判断 → 不合格页面才进入 OCR`。
- 判断依据包括有效字符数、乱码比例、文字覆盖率、阅读顺序、图片占比与表格完整性。
- OCR 以 **PaddleOCR 为主**、**Tesseract 为备用与对照基线**（命题只要求 Tesseract，此处为超出要求的部分）。
- OCR、版面分析与 Embedding 属于**离线 Worker 任务**，与在线问答路径隔离并限制并发。

## 考虑的替代方案

| 方案 | 未采用的原因 |
| --- | --- |
| FAISS（命题参考资料中提及） | 缺少服务化的持久化与并发访问能力；项目需要多进程访问与持久化，选择服务化的 Milvus。 |
| 对所有 PDF 全量 OCR | 对带文本层的 PDF 是纯粹的算力浪费，且会把原本正确的文本替换成可能出错的 OCR 结果。 |
| 让视觉大模型直接读 PDF 替代解析流水线 | 一次请求读 PDF 无法替代项目所需的稳定分页、条文切分、版本管理、增量索引与来源定位。视觉模型只适合作为低质量 OCR 与复杂版面的补充复核。 |
| OCR 与在线问答共用同一批服务 | 会挤占在线问答资源，直接冲击「响应 ≤2 秒」目标。 |

## 后果

**正面**

- 检索能力完整，支持关键词与向量双通道。
- 避免对文本型 PDF 做无谓 OCR，节省算力并减少引入错误的环节。
- 离线任务与在线路径隔离，在线响应时间不被导入任务挤占。

**负面**

- Milvus Standalone 按官方要求需要 Docker Desktop 至少分配 **8 GB 内存**，提高了本地开发与演示的机器门槛（已通过 `.wslconfig` 分配 12 GiB 应对）。
- 页面质量判断的**阈值必须依据真实制度材料确定**，目前无法给出具体数值。
- 增加了 Compose 的服务数量（6 个），启动与排障复杂度上升。

**待办**

- 获得样本数据后评测并确定质量判断阈值。
- 分别评估文本可用率、OCR 字符错误率、条文边界、表格结构、引用定位、单页耗时与峰值内存。
- PaddleOCR 3.x 已覆盖 PDF/图片 OCR、版面检测与结构化解析，具体选择 PP-OCR、PP-Structure 还是 PaddleOCR-VL，需在数据到位后比较中文制度上的效果、CPU 内存与速度。
