# ADR-0003 覆盖率只统计、暂不设门槛

- **状态**：已接受
- **日期**：2026-10-12
- **决策者**：项目组
- **相关**：[系统接口](../api/系统接口.md) · [后端测试与覆盖率记录](../testing/后端单元测试与覆盖率.md) · [术语表](../../GLOSSARY.md)

## 背景

课程命题要求「核心模块单元测试覆盖率 ≥70%」，这是硬性验收指标（记为 NFR-4）。

但项目在引入测试工具链时处于早期阶段：

- 鉴权、文档处理、OCR、检索实现与生成 Provider **均未实现**；
- `app/main.py` 等装配代码没有测试；
- 前端只有占位页，没有业务组件。

若此时在 CI 中硬性要求 70%，流水线会在相当长的时期内持续失败。

## 决策

前后端**统一采取「先只统计与展示，暂不设 fail 门槛」**的策略：

- 覆盖率报告正常生成并作为构建产物上传（`frontend-coverage`、`backend-coverage`）；
- **不设置** `fail_under` 或等价的阈值判定；
- 「核心模块」的口径先明确为 `domain/`、`services/`、`repositories/`、`schemas/`，随实现扩展。

## 考虑的替代方案

| 方案 | 未采用的原因 |
| --- | --- |
| 立即硬卡 70% | 业务模块尚未落地时会让流水线长期变红。**持续失败的检查等于没有检查**，会训练团队忽略红灯。 |
| 设一个较低基线并逐周上调 | 需要额外维护抬升计划，且基线数值本身没有技术含义；在有真实模块之前，上调的依据是人为的。 |
| 完全不统计覆盖率 | 会失去 NFR-4 的唯一度量入口，阶段材料也无法引用数据。 |

## 后果

**正面**

- 流水线保持「绿灯即有效」的信号价值。
- 覆盖率数字从第一天起可测量，阶段材料可直接引用。

**负面**

- 覆盖率缺乏**强制**约束，可能被忽视。缓解方式是评审把关，以及协作规范中「不得为了数字编写无断言价值的测试」的要求。
- 需要有人负责在合适时机把门槛抬起来——这是一个待跟踪的事项，而不是自动发生的。

**当前实际值（2026-10-12）**

| 端 | 用例数 | 覆盖率 | 状态 |
| --- | ---: | ---: | --- |
| 前端 | 19 | **95.83%** | 已超过目标 |
| 后端 | 12 | **83%** | 已超过目标 |

两者均只覆盖已实现部分（后端为 RAG 在线核心，前端为 API 客户端与应用外壳）。

**后续**

待业务模块与测试就位后逐步抬升，并在 CI 中硬性卡住。
