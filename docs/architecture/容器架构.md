# 容器架构

## 1 当前目标

当前容器配置用于统一 Windows 11 本地开发环境，并为后续迁移到 Linux 保留一致的镜像、环境变量、网络和数据卷结构。现阶段只提供后端健康检查和前端占位页，不包含 RAG、OCR 或问答业务逻辑。

## 2 服务组成

| 服务 | 作用 | 默认宿主机端口 |
| --- | --- | ---: |
| `frontend` | 构建 React 应用并通过 Nginx 提供静态页面和 API 反向代理 | 3000 |
| `backend` | 运行 FastAPI，并提供健康检查与 OpenAPI 文档 | 8000 |
| `mysql` | 保存结构化业务数据 | 3306 |
| `milvus` | 保存和检索向量 | 19530、9091 |
| `etcd` | 保存 Milvus 元数据 | 不暴露 |
| `minio` | 保存 Milvus 对象数据 | 9000、9001 |

所有服务加入 `finrag` bridge 网络，通过服务名互相访问。宿主机端口默认只绑定 `127.0.0.1`，避免开发服务意外暴露到局域网。

宿主机端口仅用于本机工具访问。容器之间始终使用服务名和容器端口通信，例如后端使用 `mysql:3306`，不会受到本地 `MYSQL_HOST_PORT` 覆盖值的影响。

## 3 启动关系

- Milvus 等待 etcd 和 MinIO 健康后启动。
- 后端等待 MySQL 健康后启动；当前健康检查不强制依赖 Milvus，便于低资源环境先进行基础开发。
- 前端等待后端健康后启动。
- Compose 只用于编排顺序，应用代码后续仍需具备连接失败重试和明确错误处理能力。

## 4 数据持久化

MySQL、etcd、MinIO 和 Milvus 均使用 Docker 命名卷。执行普通 `docker compose down` 不删除数据；执行 `docker compose down -v` 会删除全部本地服务数据，操作前必须确认。

## 5 跨环境约束

- Dockerfile 和 Compose 不使用 Windows 盘符或宿主机绝对路径。
- 配置通过 `.env` 注入，真实密钥不进入仓库和镜像。
- 开发环境默认端口可以覆盖，容器内部端口和服务名保持稳定。
- 云服务器规格明确后，再补充资源限制、TLS、正式密钥管理、备份、日志和监控配置。

## 6 镜像构建与验证

- 后端镜像基于 Python 3.12，在构建阶段安装 FastAPI 运行依赖并复制应用代码。
- 前端镜像先在 Node.js 构建阶段分别检查浏览器代码和 Vite 配置的 TypeScript 类型，再生成生产静态文件；运行阶段只保留 Nginx 和构建产物。
- Nginx 将 `/api/` 请求转发至 `backend:8000`，其他请求提供前端静态页面。
- 健康检查在容器内部使用明确的 IPv4 回环地址，避免不同环境中 `localhost` 优先解析为 IPv6 而产生误判。

当前配置已经在 Windows 11 + Docker Desktop 环境完成全量构建和启动验证，MySQL、etcd、MinIO、Milvus、backend 与 frontend 均能进入 `healthy` 状态。跨 Linux 环境的正式部署验证将在服务器规格明确后进行。
