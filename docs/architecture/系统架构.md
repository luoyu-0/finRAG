# 系统架构

## 1 目标与当前边界

本系统面向公开金融制度材料，提供文档导入、解析与 OCR、知识库构建、混合检索、自然语言问答、来源溯源、制度时效性管理以及用户登录和权限控制。

当前仓库已实现后端健康检查、前端登录与问答界面、MySQL 用户与刷新会话、问答 HTTP 路由、Docker Compose 基础环境、RAG 在线核心编排、Milvus 向量检索、MySQL 中文关键词检索、BGE Embedding、DeepSeek 生成适配器和 TXT/文字型 PDF 离线索引导入。独立文件解析流程已有 PaddleOCR，扫描件结果尚未接入在线索引；Reranker 和导入管理界面仍待接入。缺少 DeepSeek Key 时问答返回 `503`。

## 2 逻辑模块与计划目录

```text
backend/app/
├─ api/v1/
│  ├─ auth.py                 # 登录、刷新、退出和密码修改
│  ├─ users.py                # 当前用户和管理员用户管理
│  ├─ documents.py            # 文档与导入任务接口
│  └─ qa.py                   # 问答、引用、历史和收藏接口
├─ core/
│  ├─ config.py               # 环境配置
│  ├─ security.py             # 密码哈希、Token 与鉴权依赖
│  └─ exceptions.py           # 统一异常与错误码
├─ domain/                    # 用户、文档、制度版本和会话领域规则
├─ repositories/              # MySQL、Milvus 数据访问抽象
├─ schemas/                   # Pydantic 请求与响应模型
├─ services/
│  ├─ auth/                   # 登录、会话、权限与账户安全
│  ├─ documents/
│  │  ├─ parsers/             # PDF、DOCX、TXT 等原生解析
│  │  └─ quality/             # 页面质量与 OCR 路由判断
│  ├─ ocr/
│  │  └─ providers/           # PaddleOCR、Tesseract 等适配器
│  └─ rag/                    # 检索、重排、生成与溯源编排
└─ workers/                   # 离线导入、OCR、Embedding 和索引任务

frontend/src/
├─ api/                       # 统一 HTTP 客户端及领域接口
├─ components/                # 通用组件
├─ features/
│  ├─ auth/                   # 登录、退出和会话恢复
│  ├─ users/                  # 用户管理
│  ├─ knowledge-base/         # 文档和知识库管理
│  └─ qa/                     # 问答、引用、历史和收藏
├─ pages/                     # 页面入口
├─ router/                    # 路由和角色守卫
├─ stores/                    # 鉴权及页面状态
└─ types/                     # 前端公共类型
```

API 层只负责协议转换和鉴权入口，业务规则位于 Service/Domain，数据库与向量库访问位于 Repository。LLM、Embedding、OCR 和向量存储均通过 Provider 或 Repository 隔离。

## 3 容器与服务关系

| 服务 | 作用 | 默认宿主机端口 |
| --- | --- | ---: |
| `frontend` | Nginx 提供 React 静态页面并反向代理 `/api/` | 3000 |
| `backend` | FastAPI、鉴权、RAG 和文档任务入口 | 8000 |
| `mysql` | 用户、会话、文档元数据和业务状态 | 3306 |
| `milvus` | 向量与检索字段 | 19530、9091 |
| `etcd` | Milvus 元数据 | 不暴露 |
| `minio` | Milvus 对象数据 | 9000、9001 |

所有服务加入 `finrag` bridge 网络，通过服务名和容器端口互访。宿主机端口默认只绑定 `127.0.0.1`，可在本地 `.env` 覆盖；例如宿主机将 MySQL 映射到 `3307` 时，backend 仍使用 `mysql:3306`。

启动依赖为：Milvus 等待 etcd 和 MinIO，backend 等待 MySQL 与 Milvus，frontend 等待 backend。应用代码仍须处理运行中断线、超时和重试，不能只依赖 Compose 的启动顺序。

## 4 数据归属与持久化

- MySQL：用户、Refresh Session、文档与版本、导入任务、问答历史、收藏、制度状态和稳定 ID 映射。
- Milvus：Chunk 向量及检索所需字段，不保存密码、Token 或用户个人资料。
- MinIO：Milvus 对象数据；原始制度文件的长期存储方式在数据到位后再评审。
- Docker 命名卷：保存 MySQL、etcd、MinIO 和 Milvus 数据；`docker compose down -v` 会删除本地卷。

文档、版本和 Chunk 使用稳定 ID 关联。问答历史和收藏绑定 `user_id`，导入任务及文档记录保留 `created_by`，普通用户只能访问自己的用户数据。

## 5 用户与鉴权

### 5.1 最小方案

- 使用本地账户和密码登录；默认创建 `admin / finrag2026`，其他用户可公开注册普通账户。
- 角色仅包含 `admin` 和 `user`：管理员维护用户与知识库，普通用户使用问答、历史和收藏。
- 健康检查、登录、注册和刷新允许匿名访问，其他业务接口默认要求鉴权。
- 鉴权属于 backend 内部模块，不新增独立身份服务容器。

### 5.2 会话

- Access Token：建议 15 分钟有效的 JWT，前端只保存在内存中，通过 `Authorization: Bearer` 发送。
- Refresh Token：建议 7 天有效的高熵随机字符串，通过 `HttpOnly`、`SameSite=Lax` Cookie 传递；数据库只保存哈希、到期时间和撤销状态。
- 刷新时轮换 Refresh Token；退出、改密、禁用账户或管理员撤销会话后，使相关 Refresh Session 失效。
- 本地 HTTP 可通过配置关闭 Cookie 的 `Secure`；Linux 正式环境必须使用 HTTPS 和 `Secure` Cookie。

### 5.3 核心数据

`users` 至少包含稳定 ID、唯一用户名、Argon2id 密码哈希、展示名称、角色、状态、密码变更时间、最近登录时间和 UTC 审计时间。`user_sessions` 至少包含用户 ID、Refresh Token 哈希、到期与撤销时间、创建与最近使用时间；IP 和 User-Agent 仅作为可选、有限期安全审计数据。

### 5.4 权限矩阵

| 能力 | 匿名 | `user` | `admin` |
| --- | :---: | :---: | :---: |
| 健康检查、登录、注册、刷新 | 是 | 是 | 是 |
| 本人资料、密码、问答、历史和收藏 | 否 | 是 | 是 |
| 文档导入、知识库和索引维护 | 否 | 否 | 是 |
| 用户创建、禁用和会话撤销 | 否 | 否 | 是 |

权限必须由后端执行。前端路由守卫和按钮隐藏只改善交互，不构成授权控制。登录错误使用统一提示并限速，日志不得记录密码、完整 Token 或 Cookie；本地开发允许固定签名密钥，正式环境仍须使用独立环境变量。

## 6 文档解析、PDF 与 OCR

### 6.1 调研结论

OCR 仍有必要，但不对所有 PDF 全量执行。推荐“原生文本提取优先、逐页质量判断、OCR 兜底、复杂版面专项解析”。

截至 2026 年 10 月，DeepSeek 官方 `deepseek-flash` 支持 JPEG、PNG、GIF 和 WebP 图像输入，但 Files API 未将 PDF 列为支持格式。因此当前 DeepSeek API 不能直接接收 PDF，只能先提取文本，或把页面渲染为图片后交给视觉模型。Gemini 等部分模型已有原生 PDF 理解能力，但一次请求读取 PDF 不能替代本项目所需的稳定分页、条文切分、版本管理、增量索引和来源定位。

### 6.2 路由策略

| 输入 | 默认处理 | OCR |
| --- | --- | --- |
| 可靠文本层 PDF | 按页提取文本、坐标和元数据 | 不使用 |
| 纯扫描 PDF | 页面渲染、文字识别和版面分析 | 使用 |
| 混合 PDF | 逐页判断，失败页面进入 OCR | 部分使用 |
| 复杂表格、双栏、印章、公式 | 原生提取加版面分析，必要时视觉模型复核 | 按质量决定 |
| JPG、PNG 等图片 | 图像预处理、OCR 和版面分析 | 使用 |
| TXT、Markdown、DOCX | 对应解析器提取结构 | 不使用 |

判断依据包括有效字符数、乱码比例、文字覆盖率、阅读顺序、图片占比和表格完整性。阈值必须在获得真实制度材料后评测确定。

### 6.3 处理流水线

```text
文件接收与哈希
  → 类型识别和安全校验
  → PDF 按页原生文本/坐标提取
  → 页面质量判断
      ├─ 合格：清洗和结构恢复
      └─ 不合格：页面渲染 → OCR/版面分析 → 质量复核
  → 标题、条文、表格和页码归一化
  → Chunk、Embedding 和索引
```

原文件、原生提取文本、OCR 文本、坐标、页码、解析告警和人工修订保持关联。每个 Chunk 可追溯至 `document_id`、`version_id`、页码、条文编号和解析方式。

### 6.4 技术方向

保留 PaddleOCR 为主、Tesseract 为对照基线。PaddleOCR 3.x 已覆盖 PDF/图片 OCR、版面检测、表格和结构化文档解析；具体选择 PP-OCR、PP-Structure 或 PaddleOCR-VL，应在数据到位后比较中文制度效果、CPU 内存和速度。视觉模型只作为低质量 OCR、复杂表格、图表和印章的补充复核，不作为唯一事实来源。

OCR 与版面分析属于离线任务，与在线问答隔离并限制并发。Embedding 在离线索引导入和在线查询中使用同一模型；BGE 权重在构建后端镜像时预下载，不进入 Git。首次下载第三方模型前按项目规则征得用户确认。

## 7 跨环境和验证

- Dockerfile 与 Compose 不依赖 Windows 盘符或宿主机绝对路径。
- 配置和密钥通过环境变量注入，示例文件不包含真实凭据。
- 当前配置已在 Windows 11 + Docker Desktop 完成全量构建，六个服务均可进入 `healthy`。
- Linux 服务器规格确定后，再验证资源限制、HTTPS、正式密钥管理、备份、日志和监控。
- 获得样本数据后，分别评估文本可用率、OCR 字符错误率、条文边界、表格结构、引用定位、单页耗时与峰值内存。

## 8 RAG 在线核心流程

在线问答核心采用端口与编排分离的结构，不直接依赖 DeepSeek SDK、LangChain、Milvus 客户端或文档处理实现：

```text
查询与有效期过滤条件
  → 并行关键词/向量检索端口
  → 对返回结果再次执行有效状态过滤
  → Reciprocal Rank Fusion 融合去重
  → 可选 Reranker
  → 按字符与条目预算组装带标签上下文
  → AnswerGenerator 生成
  → 校验引用标签并输出 Citation
  → 计算证据支持度
```

检索端口负责把过滤条件下推到实际存储实现，编排层再次过滤属于防御性校验，避免失效制度因适配器缺陷进入生成上下文。关键词通道使用 MySQL 8.4 ngram 全文索引；向量通道使用 BGE 与 Milvus，结果由 RRF 融合。TXT 和文字型 PDF 的原生解析、Chunk 生产、BGE Embedding 与 Milvus 写入由离线导入命令提供；无文字层页面记录告警并跳过。MySQL 保存文档和 Chunk 元数据，Milvus 保存向量及检索所需字段；导入按文件相对路径和内容摘要生成稳定 ID。

没有有效证据时不调用 LLM，返回明确的无依据结果。生成器只能引用本次上下文中的 `S1`、`S2` 等标签；出现未知标签视为 Provider 契约错误。证据支持度综合融合相关性和检索通道一致性，仅表示证据支持强弱，不代表答案正确概率，后续需要用固定评测集校准阈值。

当前已完成上述核心领域对象、检索/生成端口、RRF 融合、上下文预算、无证据拒答、引用校验、证据支持度和单通道故障降级。未实现部分通过 Protocol 边界隔离，不使用临时 Mock 作为生产实现。
