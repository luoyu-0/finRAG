# 系统架构

## 1 目标与当前边界

本系统面向公开金融制度材料，提供文档导入、解析与 OCR、知识库构建、混合检索、自然语言问答、来源溯源、制度时效性管理以及用户登录和权限控制。

当前仓库已实现后端健康检查、登录/注册/刷新/退出、当前用户查询、问答接口、MySQL 问答记录写入、TXT/PDF 命令行导入、选择性 PaddleOCR、BGE Embedding、Milvus 向量检索、MySQL 中文关键词检索和 DeepSeek 生成。前端已有知识库、导入、历史、收藏页面，但对应后端路由尚未实现，真实模式下无法完成这些页面的业务操作；测试模式或 `VITE_DEMO=1` 可使用演示数据。Reranker 只有可选端口，尚无生产实现。缺少 DeepSeek Key 时问答返回 `503`。

## 2 当前代码目录

```text
backend/app/
├─ api/v1/
│  ├─ auth.py                 # 登录、刷新、退出和密码修改
│  ├─ users.py                # 当前用户查询
│  └─ qa.py                   # 问答接口与历史记录写入
├─ core/

│  └─ exceptions.py           # 统一异常与错误码
├─ domain/                    # RAG 查询、检索命中与回答对象
├─ repositories/              # MySQL 模型及关键词/Milvus 检索实现
├─ schemas/                   # Pydantic 请求与响应模型
├─ services/
│  ├─ auth/                   # 登录、会话、权限与账户安全

│  │  └─ native_import.py     # TXT/PDF 解析与分块

frontend/src/
├─ api/                       # 统一 HTTP 客户端及领域接口
├─ components/                # 通用组件
├─ features/
```

API 层只负责协议转换和鉴权入口，业务规则位于 Service/Domain，数据库与向量库访问位于 Repository。LLM、Embedding、OCR 和向量存储均通过 Provider 或 Repository 隔离。

## 3 容器与服务关系

| 服务 | 作用 | 默认宿主机端口 |
| --- | --- | ---: |
| `frontend` | Nginx 提供 React 静态页面并反向代理 `/api/` | 3000 |
| `backend` | FastAPI、鉴权、RAG 和文档任务入口 | 8000 |
| `mysql` | 用户、会话、文档元数据和业务状态 | 3306 |
| `milvus` | 向量与检索字段 | 19530、9091 |
| `etcd` | Milvus 元数据 | 不暴露 |
| `minio` | Milvus 对象数据 | 9000、19001（容器内 9001） |

所有服务加入 `finrag` bridge 网络，通过服务名和容器端口互访。宿主机端口默认只绑定 `127.0.0.1`，可在本地 `.env` 覆盖；例如宿主机将 MySQL 映射到 `3307` 时，backend 仍使用 `mysql:3306`。

启动依赖为：Milvus 等待 etcd 和 MinIO，backend 等待 MySQL 与 Milvus，frontend 等待 backend。应用代码仍须处理运行中断线、超时和重试，不能只依赖 Compose 的启动顺序。

## 4 数据归属与持久化

- MySQL：用户、Refresh Session、导入文档与分块元数据、问答历史写入。当前没有导入任务表或收藏表；问答历史尚无读取接口。
- Milvus：Chunk 向量及检索所需字段，不保存密码、Token 或用户个人资料。
- MinIO：Milvus 对象数据；原始制度文件的长期存储方式在数据到位后再评审。
- Docker 命名卷：保存 MySQL、etcd、MinIO、Milvus 数据及 OCR 模型缓存；`docker compose down -v` 会删除本地卷。

文档、版本和 Chunk 使用稳定 ID 关联。问答记录绑定 `user_id`，但读取和删除接口尚未实现。当前导入器按本地相对路径和内容摘要生成 ID，未建立上传用户归属字段。

## 5 用户与鉴权

### 5.1 最小方案

- 使用本地账户和密码登录；默认创建 `admin / finrag2026`，其他用户可公开注册普通账户。
- 角色值包含 `admin` 和 `user`；后端当前未提供用户管理、知识库管理、历史查询或收藏路由。
- 健康检查、登录、注册和刷新允许匿名访问，其他业务接口默认要求鉴权。
- 鉴权属于 backend 内部模块，不新增独立身份服务容器。

### 5.2 会话

- Access Token：建议 15 分钟有效的 JWT，前端只保存在内存中，通过 `Authorization: Bearer` 发送。
- Refresh Token：建议 7 天有效的高熵随机字符串，通过 `HttpOnly`、`SameSite=Lax` Cookie 传递；数据库只保存哈希、到期时间和撤销状态。
- 刷新时轮换 Refresh Token；退出时撤销当前会话。改密、禁用账户和管理员撤销会话接口尚未实现。
- 本地 HTTP 可通过配置关闭 Cookie 的 `Secure`；Linux 正式环境必须使用 HTTPS 和 `Secure` Cookie。

### 5.3 核心数据

当前 `users` 表保存 ID、唯一用户名、密码哈希、展示名称、角色、状态和创建时间；`user_sessions` 保存用户 ID、Token 家族、Token 摘要、到期、使用、撤销及创建时间。密码变更时间、最近登录时间、IP 和 User-Agent 尚未入库。

### 5.4 权限矩阵

| 能力 | 匿名 | `user` | `admin` |
| --- | :---: | :---: | :---: |
| 健康检查、登录、注册、刷新 | 是 | 是 | 是 |
| 本人资料查询、问答 | 否 | 是 | 是 |
| 命令行离线导入 | 不经 HTTP 鉴权 | 不经 HTTP 鉴权 | 不经 HTTP 鉴权 |
| 改密、用户管理、知识库管理、历史查询和收藏 | 尚无后端路由 | 尚无后端路由 | 尚无后端路由 |

权限必须由后端执行。前端路由守卫和按钮隐藏只改善交互，不构成授权控制。登录错误使用统一提示并限速，日志不得记录密码、完整 Token 或 Cookie；本地开发允许固定签名密钥，正式环境仍须使用独立环境变量。

## 6 文档解析、PDF 与 OCR

### 6.1 调研结论

OCR 仍有必要，但不对所有 PDF 全量执行。推荐“原生文本提取优先、逐页质量判断、OCR 兜底、复杂版面专项解析”。

当前项目只向 DeepSeek 发送问题与检索到的文本证据，不直接把 PDF 或图片发送给生成模型。PDF 在离线导入阶段提取文字；视觉模型直读文档仍属于未实施的备选方向。

### 6.2 路由策略

| 输入 | 默认处理 | OCR |
| --- | --- | --- |
| 有文字层 PDF | 按页提取文字；暂不保存坐标或版面结构 | 不使用 |
| 无文字层 PDF 页 | 使用 `--ocr` 时渲染页面并调用 PaddleOCR | 使用 |
| 混合 PDF | 按页判断是否有非空文字 | 仅空文字页使用 |
| 复杂表格、双栏、印章、公式 | 当前仅作常规文字提取，质量需人工核对 | 无专项处理 |
| TXT | UTF-8 解码，失败时尝试 GB18030 | 不使用 |
| 图片、Markdown、DOCX、DOC、WPS | 当前命令行索引导入器不支持 | 不适用 |

当前 OCR 路由条件是 PDF 页的提取文本为空；乱码比例、阅读顺序和表格完整性等质量指标尚未实现。改进阈值需结合实际文档评测。

### 6.3 处理流水线

```text
文件接收与哈希
  → 扩展名与 50 MB 大小检查
  → 同一知识库内按 SHA-256 去重（重复内容直接跳过）
  → TXT 解码或 PDF 逐页提取文本
  → PDF 空文字页（仅 --ocr）：渲染 → PaddleOCR → 复核告警
  → 按章、节、条及换行/标点切分；每块不超过 500 字符
  → Chunk、Embedding 和索引
```

原文件保留在本地 `data/raw/`，导入索引保存分块正文、文档/版本 ID、页码、条文编号及来源链接；解析告警在命令行输出。当前没有持久化 OCR 坐标、独立 OCR 原文或人工修订记录。TXT 分块没有页码。

### 6.4 技术方向

当前离线索引导入使用 PP-OCRv5 mobile 检测与识别模型处理无文字层页面；与默认中型模型的两页样本对比显示速度更快，仍需扩大样本评估识别错误率。Tesseract、PP-Structure、PaddleOCR-VL、复杂表格专项解析和视觉模型复核均未接入。

OCR 在一次性离线导入容器中运行，与在线问答进程隔离；当前没有独立版面分析服务或后台任务队列。Embedding 在离线索引导入和在线查询中使用同一模型；BGE 权重在构建后端镜像时预下载，不进入 Git。

## 7 跨环境和验证

- Dockerfile 与 Compose 不依赖 Windows 盘符或宿主机绝对路径。
- 配置和密钥通过环境变量注入，示例文件不包含真实凭据。
- 当前配置已在 Windows 11 + Docker Desktop 完成全量构建，六个服务均可进入 `healthy`。
- 后端镜像构建时安装 PaddleOCR/OpenCV 所需的 Debian 系统库。Compose 的 Debian 软件源可通过 `DEBIAN_MIRROR` 与 `DEBIAN_SECURITY_MIRROR` 构建参数配置；Windows 启动脚本默认复用镜像，需要重建时使用 `-Build`。构建耗时与健康状态见[容器构建耗时回归](../testing/容器构建耗时回归.md)。
- Linux 服务器规格确定后，再验证资源限制、HTTPS、正式密钥管理、备份、日志和监控。
- 已建立 50 题开发基准集与后端评测命令；其来源、引用和字面相似度结果见[分块策略与问答基准](../testing/分块策略与问答基准.md)。OCR 字符错误率、表格结构和最终验收指标仍需单独评估。

## 8 RAG 在线核心流程

在线问答采用 LangChain LCEL（`langchain-core`）编排，`RagService.answer` 通过 `ainvoke` 依次执行混合检索、融合与上下文、生成与引用校验三个节点。每次请求独立传递上下文和告警，领域对象与 Repository 端口保持独立。生成 Provider 使用 `langchain-deepseek` 的 `ChatDeepSeek`，由 `ChatPromptTemplate → 聊天模型 → 严格 JSON 解析` 组成子链。

```text
查询与有效期过滤条件
  → 并行关键词/向量检索端口
  → 对返回结果再次执行有效状态过滤
  → Reciprocal Rank Fusion 融合去重
  → 可选 Reranker
  → 按字符与条目预算组装带标签上下文
  → AnswerGenerator：LangChain 提示模板与 ChatDeepSeek 异步生成
  → 校验引用标签并输出 Citation
  → 计算证据支持度
```

检索端口负责把过滤条件下推到实际存储实现，编排层再次过滤属于防御性校验，避免失效制度因适配器缺陷进入生成上下文。关键词通道使用 MySQL 8.4 ngram 全文索引；向量通道使用 BGE 与 Milvus，结果由 RRF 融合。TXT 和 PDF 的原生解析、Chunk 生产、BGE Embedding 与 Milvus 写入由离线导入命令提供；启用 OCR 后，无文字层的 PDF 页面经渲染和识别后入库，并记录需人工复核的告警。MySQL 保存文档和 Chunk 元数据，Milvus 保存向量及检索所需字段；导入按文件相对路径和内容摘要生成稳定 ID。

没有有效证据时不调用 LLM，返回明确的无依据结果。生成器只能引用本次上下文中的 `S1`、`S2` 等标签；出现未知标签视为 Provider 契约错误。证据支持度综合融合相关性和检索通道一致性，仅表示证据支持强弱，不代表答案正确概率，后续需要用固定评测集校准阈值。

当前已完成上述核心领域对象、检索/生成端口、RRF 融合、上下文预算、无证据拒答、引用校验、证据支持度和单通道故障降级。未实现部分通过 Protocol 边界隔离，不使用临时 Mock 作为生产实现。

同一知识库内相同文件字节只保留一份索引，别名文件不生成新文档。MySQL 连接锁保护去重检查与写入，不改变现有表结构。`--rebuild` 可显式重建保留路径以更新元数据或分块规则，重复副本仍跳过。评测按知识库及来源内容哈希定位保留文档，避免重复文件名影响来源命中判断。
